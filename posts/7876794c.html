PHP2Shell 漏洞分析：两个 9.2 分 RCE 的技术全貌

引言

2026 年 10 月 21 日，UTC 14:00。

PHP 官方没有像往常那样发一篇云淡风轻的 “Released!”，而是直接甩出一句：

PHP 8.5.12、8.4.27、8.3.36、8.2.35 修复两个可导致未授权远程代码执行的严重漏洞。所有 PHP 用户请立即更新。

没有"建议"，没有"酌情"，就是立即。

社区给它们起了个名字——PHP2Shell。

Wiz 研究团队在报告里写了一句话，我觉得比任何评分都更能说明问题：

这些发现堪称 PHP 历史上最严重的漏洞之一，甚至可以说是软件史上最严重的漏洞之一。

一、先把事实摆清楚

1.1 基础信息

项目 内容
漏洞编号 CVE-2026-109618、CVE-2026-109619
社区代号 PHP2Shell
发现方 Calif（GPT-5.6 Sol）、Wiz Research（Wiz Atlas + Gemini 4 Argon + GPT-5.6 Sol）
披露时间 2026-10-21 14:17 UTC
漏洞类型 未授权远程代码执行（RCE）+ 远程进程内存泄露
CWE 分类 CWE-416（Use After Free）、CWE-755（异常处理不当）、CWE-824（未初始化指针访问）、CWE-1325（资源锁管理不当）
官方修复 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12

1.2 为什么是"两个"评分，不是"一个"

这一点很容易被中文二手报道写乱，我单独说明。

同一组漏洞，存在两套评分标准并存的情况：

评分来源 标准 分数 严重度
PHP 官方（security@php.net） CVSS v4.0 9.2 CRITICAL
NVD / NIST CVSS v3.1 9.8（109618）/ 8.1（109619） CRITICAL / HIGH

两套分数不一致不是谁错了，而是算法不同、评估维度不同：

  • CVSS v4.0 引入了 AT（Attack Requirements，攻击前置条件）这个维度。PHP 官方给 109618 打了 AC:H（攻击复杂度高）+ AT:P（需要前置条件），这两项拉低了分数，最终算出 9.2。
  • CVSS v3.1 没这个维度，109618 被 NIST 评为 AC:L（攻击复杂度低）、AV:N/PR:N/UI:N，直接算出 9.8。

所以准确的说法是：

两个漏洞的 CVSS v4.0 评分都是 9.2（官方口径）；按 v3.1 口径，109618 是 9.8，109619 是 8.1。

不管用哪套标准，都落在"严重"区间。别被数字差异迷惑。

1.3 影响范围有多大

官方原话：

所有处理 Web 请求的 PHP 安装，包括 PHP-FPM、Apache with mod_php、php-cgi、FrankenPHP 和 LiteSpeed。

Wiz 的补充更狠：

过去十年发布的每一个 PHP 版本都至少受其中一个漏洞影响，最早可追溯到 PHP 5.4。

而 NVD 的配置数据佐证了这一点——CVE-2026-109619 的受影响版本区间写的是 versionStartIncluding: 5.4.0。

至于覆盖面：PHP 支撑着全球约 70% 的网站，包括 WordPress、Joomla、Drupal，以及维基百科背后的 MediaWiki。

1.4 官方给的两个 GHSA 编号

  • CVE-2026-109618 → GHSA-w8hw-w9fx-j79w
  • CVE-2026-109619 → GHSA-6wmf-4rv5-p3rp

还有一句必须原样引用的话：

没有完整的缓解措施，更新是唯一安全的选择。
（There are no complete mitigations, updating is the only safe choice.）

二、底层原理：必须先把这三个概念讲透

要看懂后面的四个 bug，得先理解 PHP 处理请求的三件事。这一节是全文的地基，建议别跳。

2.1 概念一：longjmp() —— PHP 是怎么"一键放弃"的

大多数语言遇到内存不足，会抛一个异常，然后一层层往上冒泡，每层都有机会 catch、清理、释放资源。

PHP 不是。

PHP 处理 OOM 用的是 C 语言的 longjmp()。

longjmp() 是什么？简单说就是一个**“跳跃式返回”——它不需要一层层退栈，可以直接从调用栈深处瞬间跳回**事先用 setjmp() 记下的那个位置。

NVD 对 109618 的描述第一句就是：

PHP uses longjmp() for out-of-memory (OOM) errors to exit the current context and abort handling of the request.

翻译：PHP 用 longjmp() 处理 OOM 错误，直接退出当前上下文、放弃处理这个请求。

这个设计本身没问题，甚至是性能导向的合理选择（OOM 时栈可能已不可靠，逐层清理反而危险）。

但它带来一个致命副作用：

longjmp() 会直接跳过你原本打算执行的清理代码。

想象你正在写文件：

如果第 2 步 OOM，第 4 步的"关闭文件"就永远不会跑。

在 PHP 里，被跳过的可能是：计数递增后的状态、指针赋值、标志位设置、堆栈记录。

于是——请求的内存堆被销毁了，但某些全局状态还指着它。

这就是后面四个 bug 共同的根源。

2.2 概念二：请求堆（request heap）的生命周期

PHP 每个请求的内存是成批分配、成批销毁的，不是一个个 malloc/free。

请求开始时，PHP 开一个"内存池"（request heap）；请求结束时，整个池一次性销毁。这个设计叫 arena allocator，非常快。

好处：不用逐个释放，天然没有内存碎片。
坏处：只要你漏了一个指针，它就变成悬空指针（dangling pointer），而且指向的那块内存马上会被下一个请求重新分配、重新填上别人的数据。

而 PHP 的进程模型是 worker 复用——PHP-FPM、mod_php 都是一个 worker 连续处理成百上千个请求。

这两点一叠加，就构成了经典的 跨请求 Use-After-Free（UAF）：

关键在于：攻击者不知道下一个请求是谁发的。 这正是这个漏洞"脏"的地方——它不只是打自己，是污染整个进程。

2.3 概念三：EG() / CG() / BG() / PS() —— 那些"全局状态"

PHP 源码里到处是这类宏，它们是进程级 / 线程级的全局变量：

宏 含义 存放什么
EG(x) Executor Globals 执行器全局状态，如 EG(last_fatal_error_backtrace)
CG(x) Compiler Globals 编译器全局状态，如 CG(map_ptr_last)
BG(x) Basic Globals 基础全局，如 BG(unserialize)
PS(x) PHP Session globals 会话状态，如 PS(id)

问题在于：这些全局状态的生命周期 ≠ 请求的生命周期。

设计上，它们应该在每个请求开始时被重置、请求结束时被清理。

但 longjmp() 会跳过清理。于是——

请求堆没了，全局状态还在指着它。 下一个请求进来，全局状态还没被重置，就会用到失效的指针。

下面四个 bug，全是这个模式的四种变体。

三、四个 bug 的逐条拆解

Wiz 一共报告了 4 个可利用的 bug，归到 2 个 CVE 下。

先看总览表：

编号 Bug 攻击者能做什么 已演示
CVE-2026-109618 上传进度 unserializer UAF 破坏进程内存、执行代码 WordPress / Drupal / Joomla 未认证 RCE
CVE-2026-109618 远程进程内存泄露 未认证读取 PHP worker 内存 应用无关的内存泄露
CVE-2026-109619 致命错误回溯 UAF 破坏进程内存、执行代码 Drupal 未认证 RCE
CVE-2026-109619 OPcache 类型混淆 破坏共享 PHP 状态、执行代码 WordPress 未认证 RCE

3.1 Bug ①：上传进度 unserializer Use-After-Free

所属 CVE：109618

这是最复杂、也是被用来打通 WordPress 和 Joomla 的那个。

机制拆解：

  1. PHP 的 Session 模块处理上传进度时，会在一个"过早的初始化窗口"里解码 session 数据。
  2. 解码器把自己需要的记录写进全局 BG(unserialize)。
  3. 此时如果发生致命的内存分配失败（OOM），longjmp() 会打断这条路径 → 请求堆被销毁 → 但 BG(unserialize) 这个全局状态已经被发布了，仍然指着刚被销毁的堆。
  4. 同一个 worker 处理下一个请求时，PHP 会把"攻击者已经重新占用的内存"当成仍然有效的 unserializer 记录来用。

Wiz 的原话：

The stale state becomes a powerful memory-corruption primitive.
（这个陈旧状态变成了一个强大的内存破坏原语。）

它再把这一手和"内存泄露"组合起来，消除地址不确定性，最终在 WordPress、Drupal、Joomla 上都拿到了未认证 RCE。

为什么这个特别吓人： 它发生在应用层之下。你的 WAF、你的入口过滤、你的框架中间件，全都在这个位置之后才轮到执行。

3.2 Bug ②：远程进程内存泄露（Heartbleed 式）

所属 CVE：109618

这个不需要 RCE，就能直接偷数据。

机制拆解：

  1. PHP 在处理请求启动阶段（正常模块初始化完成之前）就解析 RFC1867 的 multipart 请求。
  2. 上传进度处理可以在这个极早的阶段初始化 Session 状态，并把 session ID 存进 PS(id)。
  3. 此时 OOM 中断请求 → 清理没做完 → 请求堆被销毁 → PS(id) 指向已被释放的内存。
  4. 同一 worker 处理下一个 multipart 请求时，会在 Session 正常初始化重置该指针之前，走到上传进度的清理路径。
  5. PHP 把那个陈旧的指针和长度当作有效的 zend_string，把回收后的堆内容 URL 编码后塞进 PHPSESSID 响应 Cookie。

结果：攻击者的响应头里，带回了属于别人请求的活内存。

里面可能有：密码、认证令牌、API 密钥、证书。

Wiz 的评价（这句很关键）：

The attack works even when the application never calls session_start(), making the issue application-agnostic.
（即使应用从不调用 session_start() 也能打，这让该问题与应用无关。）

这就是它的"Heartbleed 时刻"——不需要应用配合，PHP 引擎自己就把内存漏出去了。

3.3 Bug ③：致命错误回溯 Use-After-Free

所属 CVE：109619

机制拆解：

  1. 受影响版本里，PHP 会把最近一次致命错误的回溯保留在 EG(last_fatal_error_backtrace)。
  2. 致命 OOM 会销毁请求堆，但没有把这个 executor 全局值取消定义。
  3. worker 活下来了，而那个全局变量还指着上一个请求的内存。
  4. 如果同一个 worker 在下一个请求的早期产生诊断输出，就能在 executor 重新初始化之前访问到这个指针。
  5. PHP 随后销毁 / 更新这个悬空的回溯 → 顺着攻击者已经回收的内存走。

产生的跨请求 UAF 可以被发展成受控的内存破坏。Wiz 用它打穿了 Drupal。

一个容易被忽略的细节： 这条路径依赖"请求早期就产生诊断输出"。这也解释了为什么官方缓解建议里有一条是"清掉那些会在初始化前产生诊断的配置"——以及为什么用 error_reporting 或 @ 去屏蔽报错是没用的（报错已经产生并触发了路径，只是不显示而已）。

3.4 Bug ④：OPcache 类型混淆

所属 CVE：109619

这个最精妙，因为它跨的是 worker 之间，不是请求之间。

背景：OPcache 把编译好的 PHP 结构放进共享内存，并用"索引"指向每个 worker 私有的运行时指针表。worker 之间通过一个**共享的 frontier（前沿指针）**来协调这些索引。

机制拆解：

  1. 在 zend_accel_script_persist() 期间，PHP 先推进进程本地的 CG(map_ptr_last)。
  2. 要等持久化完成之后，才发布对应的共享 frontier。
  3. 如果在这两个动作之间发生内存分配失败 → 进程本地的推进留下了，但共享状态还认为那些槽位可用。
  4. 另一个 worker 后来把这些槽位复用给不同类型的运行时对象。
  5. 陈旧的共享元数据于是解析出一个类型错误的指针。

结果：跨 worker 的类型混淆（type confusion），破坏共享的 OPcache 状态。Wiz 用它打通了 WordPress。

为什么这个最"优雅"： 前三个 bug 都是同一个 worker 内的跨请求污染，这个直接跨进程共享内存。一个 worker 被污染，所有 worker 都可能中招。

3.5 一个重要的补充：这只是 4 个，不是全部

Wiz 明确说了：

While this blog covers only four instances of exploitable bugs (grouped under two CVEs) that follow this problematic pattern, there are other tracked, and likely untracked, variants of this issue in the PHP codebase.

翻译：这 4 个只是已报告的，代码库里还有已知的、以及尚未被发现的同类变体。

但好消息是：

无论如何，PHP 团队提供的补丁从根源上修复了这个问题，并在打补丁的版本中消除了所有变体。

这也是为什么官方说"更新是唯一安全选择"——补丁不是打补丁，是在核心层面堵死这一类模式。

四、为什么这次特别难修、也特别难发现

4.1 难修：动了引擎

PHP 官方把这次修复形容为——

“需要对 PHP 引擎做一次重大改动”（a major change to the PHP engine）。

不是加个 if，不是补个边界检查。是改引擎的核心内存管理逻辑。

这也解释了为什么从 8 月发现到 10 月发版，中间隔了两个月——不是拖，是真的难改。

4.2 难发现：卡在"人类极限"

Wiz 有一句话说得非常克制，但信息量极大：

这些底层缺陷已经存在了几十年，但证明其可利用性需要一条异常复杂的利用链，处于人类研究者实际能达到的边缘。

翻译：不是没人看，是看到了也打不通。

传统的"叠加多个 bug + 适配每个目标的堆布局"这条路，人工做起来成本极高、且几乎无法规模化。这也是为什么它能安静地躺十几年。

4.3 两个独立团队、同一批漏洞

这次有个很有意思的现象——同一组漏洞被两个互不通信的团队独立挖到：

团队 工具 开始时间 首洞时间
Calif / Ryan Austin GPT-5.6 Sol 2026-07-30 2026-08-01（2 天）
Wiz Research Wiz Atlas + Gemini 4 Argon + GPT-5.6 Sol 2026-08-19 当天发现，8/20 确认 Drupal RCE

两边都在 8 月报给 PHP，10 月一起公开。

这说明：不是某个模型的偶然神迹，而是"AI 审计这条路"已经能稳定复现了。

4.4 最值得记住的细节：把发现写成 SKILL.md

Calif 在挖出第一个洞之后没有收工。

他们让模型把刚刚发现的错误模式写成一份 SKILL.md——一份可复用的审计指引——然后让 Agent 拿着它，沿着同样的线索继续扫整个代码库。

结果：在上传进度那段代码里，找到了第二个洞。

这是 AI 审计和人工审计最本质的差别：

人挖到一个洞，经验留在脑子里。
AI 挖到一个洞，经验变成一份可以立刻分发给一万个 Agent 的文件。

从"找到一个点"，变成"找到一整类"。

Wiz 的说法更直接：

借助前沿 AI 模型和合适的工具，单个研究者在一周内完成了过去世界级团队需要数月才能完成的工作。

五、这套东西被做成了"一条流水线"

这次披露不像"发个公告你们自己看着办"，而是一次全球协同。

参与的包括：Google Cloud、Cloudflare、AWS、Microsoft、Automattic、Fastly、Akamai、Imperva、Vercel，以及政府侧的 CISA、ONCD。

OpenAI 推了一个五阶段框架（Patch the Planet）：

阶段 做什么
1. 验证并修复上游漏洞 确认、评估、开发并测试修复，包括用前沿模型做对抗性测试（专门找绕过补丁的方法）
2. 给受影响组织留出行动时间 判断哪些组织需要提前获知
3. 与政府协同保护关键系统 让指引触达关键基础设施运营方
4. 在受影响产品中准备更新 发行版回补、主机商测试缓解、安全厂商准备 WAF 规则
5. 补丁就绪后公开并支持部署 公开披露、提供版本检查工具、指导验证

这套流程催生了一个新概念：Defender’s Window（防御者窗口）。

传统逻辑是：发现 → 立刻公开 → 攻击者和管理员同时起跑，管理员通常输。

这次不是。8 月发现，10 月公开，中间两个月防御方全部就位。

当然，同一把刀两边都能用。OpenAI 自己也很坦白：

这凸显了 AI 如何能够发现具有互联网规模影响的安全漏洞，但同样的能力也可以帮助攻击者快速开发攻击工具和漏洞利用程序。

六、你的服务器该做什么

6.1 第一步：查版本

对照下表。只要不在修复版本或以上，你就是暴露的。

分支 安全线 你受影响的条件
PHP 8.5.x 8.5.12 < 8.5.12
PHP 8.4.x 8.4.27 < 8.4.27
PHP 8.3.x 8.3.36 < 8.3.36
PHP 8.2.x 8.2.35 < 8.2.35
PHP 8.1 / 8.0 / 7.4 官方已 EOL 全部受影响

发行版用户先看有没有跟进：

Windows 用户去 php.net/downloads 下新版二进制。

6.2 第二步：EOL 分支怎么办

注意：官方不再为 8.1 / 8.0 / 7.4 发新版。

但这次 PHP 安全团队破例，提供了最小化源码回补分支，给那些自己编译或没有 LTS 供应商的人：

  • PHP-7.4-CVE-2026-109618-109619
  • PHP-8.0-CVE-2026-109618-109619
  • PHP-8.1-CVE-2026-109618-109619

6.2.1 用面板的：宝塔面板和 1Panel 都跟上了

如果你是面板用户，这次不用自己编译。两家国内主流面板都在 1–2 天内完成了适配，而且宝塔做得比"跟一下官方包"还要多。

宝塔面板：10 月 22 日就上线了，而且是"国内独家兼补丁包"

宝塔在论坛置顶了一条公告（2026-10-22，PHP 官方发版次日）：

宝塔是国内首家针对本次漏洞手动适配旧版 PHP 安全补丁的运维面板服务商，并提供独家修复包与面板内更新方案。

这句话不是虚的。宝塔的覆盖范围远超 PHP 官方——官方只管 8.2 以上，宝塔一路补到了 PHP 7.0，甚至尝试了 PHP 5.6。

两个细节值得单独说：

① PHP 7.0–7.3 的补丁是怎么来的？
不是官方给的（官方早就 EOL 了），是宝塔基于 PHP 7.4 的官方补丁逐个函数比对、逐行回移到 7.0–7.3。这个工作量不小。

② PHP 5.6.41「宝塔 AI 修复版」这个故事很有意思。
官方从未发布过 5.6 的补丁。宝塔用 AI 辅助 + 人工代码比对的方式，在 PHP 5.6 上把这两个洞补了。因为团队缺少 5.6 的真实业务环境，所以开放测试、邀请用户反馈，装法是一条命令：

⚠️ 宝塔明确标注：该版本尚未完成真实业务场景验证，请先在测试环境跑，不要直接上生产。 如果验证稳定，约半个月后才会纳入软件商店。

宝塔的升级步骤：

  1. 进入「软件商店」→ 「已安装」
  2. 先点右上角「更新软件列表」（很多人漏这步，导致看不到新版本）
  3. 找到网站正在用的 PHP 分支，点「更新」
  4. 确认 PHP 服务已重启（没自动重启就手动重启，否则所有 worker 还在跑旧版本）
  5. 核对版本、检查扩展加载、验证登录/上传/数据库连接

⚠️ 升级前务必备份或建服务器快照。 升级会重启 PHP 服务，站点会短暂不可用，建议在业务低峰期做。

如果开了「系统加固」导致更新被拦，按提示临时关闭，升级完再打开。

Windows 面板用户注意：PHP 8.2 及以上可以在软件商店更新；但 8.1 及更早版本目前只能临时缓解（改配置、禁用相关功能），需要尽快规划迁移。

宝塔还给了三层"兜底"防护（注意：都不能替代打补丁）：

宝塔自己反复强调（原文）：

补丁升级仍是必要步骤。 首页风险中的一键加固，以及 Nginx 防火墙、系统加固、防入侵、PHP 安全告警等防护措施，都不能完整替代 PHP 安全补丁。

6.3 第三步：升不动时的缓解（降低，但不消除）

官方反复强调：没有完整缓解。 下面这些只能降低特定攻击路径的暴露面。

针对 CVE-2026-109618（OOM 相关）

补充措施：

  • 在 Web 服务器 / 代理层限制解码后的请求体大小、字段数、multipart part 数、header 数、嵌套深度
  • 这些限制必须也覆盖没有 Content-Length 的请求（很多人漏）
  • 用容器 / cgroup 限制做可用性边界，策略上只杀受影响的 worker
  • 绝对不要用 RLIMIT_AS / RLIMIT_DATA 代替——官方明确说这两个反而会触发那个有害的分配失败

针对 CVE-2026-109619（陈旧全局状态相关）

补充措施：

  • 改完必须重启所有 worker，否则等于没改（这条真的经常被忘）
  • 清掉那些会在初始化前产生诊断的无效 / 废弃配置
  • 用 error_reporting、display_errors 或 @ 屏蔽报错是无效的——报错已经产生并触发了路径
  • 修掉攻击者可达的 fatal error 和执行超时（包括回调、上传、导入处理、清理里的失败）

6.4 第四步：如果你是 SOC / 应急响应

这次漏洞跑在应用层之下，所以应用日志里几乎没有上下文。Wiz 给出的可观测信号：

信号 说明
异常 multipart 请求后紧跟内存上限错误 最典型的组合
反复出现 HTTP 500 可能是 OOM 反复触发
异常大或畸形的 PHPSESSID 响应 Cookie 内存泄露路径的直接特征（URL 编码的堆内容）
无法解释的 PHP worker 频繁重启/churn OOM 与崩溃的副作用

Wiz Sensor 1.0.12768 及以上版本内置了响应策略，可以自动终止表现出 PHP2Shell 利用特征（exploitation）的进程。

七、影响范围：这不只是"企业网站"的事

前面讲的都是技术机制。但我觉得最该被认真讲的，是这件事到底打到了谁。

因为很多人的第一反应是"我不做网站运维，跟我没关系"。

恰恰相反。

7.1 先看硬数据

指标 数据 来源
全球使用 PHP 的网站占比 约 70%（W3Techs 可识别服务端语言的站点中 69.3%） Wiz / 多源
全球公网暴露的受影响 PHP 服务器 超过 510 万台 南通大学信息化中心风险通告
受影响的最老版本 PHP 5.4（十年前） Wiz / NVD
已观测到的攻击 已有早期攻击尝试 同上
已发生的极端应对 部分国家临时下线政府官网避险 同上

"510 万台"这个数字需要单独理解一下。

它只是公网直接暴露的那部分。大量 PHP 服务跑在内网、跑在 NAT 后面、跑在容器编排里，这些根本不会被扫出来，但一旦有任何一个入口被打穿（比如一个老旧的接口、一个忘了关的测试环境），它们同样在射程内。

而且——它不需要你的应用有任何漏洞。

7.2 哪些系统在射程里

Wiz 用最新官方镜像实测打通了三套 CMS：

  • WordPress（全球 43% 的网站）
  • Drupal
  • Joomla

但这三套只是演示靶子。Wiz 反复强调：

这些平台只是说明影响，漏洞在 PHP 本身。利用不依赖于应用代码的缺陷：即使是一个只写着 “Hello World” 的应用，跑在受影响版本上也可能中招。

那顺着"什么跑在 PHP 上"往下想，射程就非常吓人了：

领域 典型系统 为什么在这里特别致命
博客 / 内容站 WordPress、Typecho、Hexo 后台、Discuz 装得多、升级懒、插件杂
电商 WooCommerce、Magento、ECShop、各类商城系统 直接持有支付与订单数据
政务 / 教育 门户站、OA、教务系统 大量老旧 PHP 7.x，且已有国家下线官网
论坛 / 社区 Discuz、phpBB、Flarum、各类自建论坛 用户数据 + 常被扫
企业官网 / 建站平台 各种"一键建站"、模板站 一个面板管几十上百个站
游戏服务端 大量游戏后台、充值页、活动页、排行页 见下节
接口 / 网关 各类 PHP 写的 API 网关、支付回调 直接暴露公网、无 WAF

**注意最后两行。**这才是很多人没意识到的地方。

7.3 游戏服务器：一个被严重低估的暴露面

"游戏服务器"听起来像是 C++ / Go 写的高性能服务，跟 PHP 没关系。

但真正跑在 PHP 上的，是游戏的外围。

一个国内中小型游戏 / 私服 / 页游 / 手游的典型架构长这样：

这些组件的共同点：

  1. 直接暴露公网（支付回调必须能被支付宝/微信访问）
  2. 直接摸钱（充值、订单、兑换码）
  3. 直接摸账号（账号中心一破，玩家账号全泄）
  4. 常常是外包或赶工产物，PHP 版本常年不升
  5. 往往没有 WAF（主站有，回调域名不一定有）

而 PHP2Shell 的第二个 bug（内存泄露）不需要 RCE 就能读进程内存。里面可能是什么？Wiz 说得很清楚：

密码、认证令牌、API 密钥、证书。

放在游戏场景里，就是：数据库密码、支付密钥、第三方 API 的 appkey、玩家 session。

一次泄露，可能等于把整套充值链路和玩家库的钥匙交出去。

7.4 一个必须说清楚的事：这不是"网站被黑"那么简单

如果只是首页被挂个马，那还属于"恶心但不致命"。

PHP2Shell 的严重性在于，它拿到的权限是 Web 工作进程的权限，而从这个位置能做的事很多：

攻击者能做的 后果
读进程内存 拿到数据库密码、API key、session、证书
写任意文件 植入 webshell、改页面、留后门
读数据库 拖库（用户表、订单表、玩家账号）
横向移动 从这台机器摸到内网其他服务
挖矿 / 建僵尸网络 你的服务器变成别人的资源
篡改内容 挂博彩、挂诈骗、挂政治内容

腾讯云的通告里有一句总结得很到位：

未经身份验证的远程攻击者利用该漏洞可在服务器上以 Web 工作进程账户身份执行任意代码，可能导致服务器完全沦陷、敏感数据泄露或恶意软件植入等危害。

“服务器完全沦陷”——不是夸张，是标准描述。

7.5 所以，谁该紧张

按优先级排一下：

优先级 谁 为什么
🔴 最高 跑 Apache + mod_php 的公网服务 官方说风险最高，已有可直接运行的利用
🔴 最高 PHP 7.x / 8.0 / 8.1 的服务 官方不再发版，只能靠面板 / 发行版回补
🟠 高 支付回调、API 网关、账号中心 直接摸钱、摸账号，常无 WAF
🟠 高 面板管理的多站点服务器 一个面板几十个站，中一个等于全中
🟡 中 WordPress / Discuz / MediaWiki 站点 量大、升级慢、插件杂
🟡 中 游戏官网 / 活动页 / 周边商城 涉及支付，且常无人维护
🟢 相对低 纯静态站、无 PHP 的服务 不受影响

如果你属于前两行——现在就去查版本，别往下读了。

八、这件事真正的意义

8.1 找漏洞的成本，塌了

互联网底层其实建立在一堆没人付钱、也没几个人认真看的代码上。

这么多年没出大事，原因特别朴素：找漏洞太贵了。

能在 PHP 内核这种地方找到可用内存漏洞的人，全世界可能就几百个。他们的时间极贵，一个洞要磨几个月。

所以很多雷能安静地埋上二十年——不是因为藏得好，是因为真的没人有空去搭理它们。

Wiz 的总结很精准：

随着 AI 降低开发和适配复杂利用所需的投入，那些曾经看起来不切实际的漏洞，变成了可行的目标。

8.2 修复能力，才是真正的瓶颈

PHP 基金会自己在复盘里承认：人手不够。

Hacker News 上有人翻出 Debian 上负责 PHP 打包的维护者的赞助页面，月赞助连 700 美元都不到。

而全球 70% 的网站，跑在这些代码上。

环节 现状
发现 被 AI 抬高了几个数量级，还在加速
修复 还是靠几个志愿者用爱发电
部署 靠全球几千万运维自己点"更新"

当发现速度远超修复和部署速度时，堆积的不是安全感，是风险。

8.3 但这次，防御者第一次跑赢了

Defender’s Window —— 这个词值得记住。

AI 8 月找到，10 月才公开。这两个月里：PHP 修好了并做了对抗性测试，云厂商备好 WAF，发行版备好回补，政府备好指引。

这是第一次，“发现得早"真的转化成了"修得从容”。

但正如 Wiz 说的——这靠的不是运气，是提前排好的协同。

九、今晚就要做的三件事

① 查版本（5 分钟）

不在安全线上？那你就是暴露状态。面向公网的优先处理。

② 先上缓解（10 分钟）

写完记得重启 worker。（真的，很多人忘）

③ 重新审视你的"老旧版本债"

这次最该记住的不是这两个 CVE 编号，而是：

AI 让"没人发现的旧洞"，变成了一个即将到期的负债。

那些你一直拖着没升的 PHP 7.4、那些没维护的内部系统、那些"反正没人看"的依赖——它们的安全性假设，建立在"没人有空来挖它"之上。

这个假设，从 2026 年开始不成立了。

结语

说点不太像安全公告的话。

以前我们总觉得，安全是"补漏洞"。一个洞，一个补丁，一次重启，完事。

但 PHP2Shell 让我意识到，这次真正被改变的不是某个 CVE，而是时间尺度。

一个埋了十几年的问题，两天被翻出来。一个"处于人类研究者极限边缘"的利用链，被一个 Agent 顺着自己写的 SKILL.md 扫了出来。

Wiz 自己把这件事和 Heartbleed、Log4Shell 并列，说它可能标志着"AI 时代的转折点"。我觉得这个类比是准的——不是因为漏洞更严重（虽然确实很严重），而是因为它重新定义了"什么才叫可利用"。

当复杂度不再构成屏障，我们过去用来判断"这个洞打不通所以先不管"的所有直觉，都需要重写。

下次深夜响警报的时候，希望你打开的不是"哪个版本又出事了"的搜索框，而是一行已经跑到最新版的 php -v。

—— 共勉。
