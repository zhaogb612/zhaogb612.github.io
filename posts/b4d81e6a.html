Hexo 博客 SEO 配置与收录排查教程

本文说明 Hexo 站点无法被搜索引擎收录的常见成因，并给出可复现的排查与修复步骤。文中配置以 Butterfly 主题为例，其他主题的原理相同。

一、适用范围

项目 说明
生成器 Hexo 6.x
部署方式 GitHub Pages（用户名.github.io）
主题 Butterfly 4.x（用于说明站长验证的配置位置）

若站点已绑定自有域名并完成备案，收录表现与本文描述不同，相关差异见第十一节。

二、问题现象

站点可正常访问，文章页面也能打开，但在搜索引擎中检索站点名称或文章标题时无法找到结果。

这类现象通常与内容质量无关，而是站点的基础配置存在缺陷，导致爬虫无法识别页面的规范地址。

三、排查步骤：三项自检

修改任何配置之前，应先确认爬虫实际抓取到的内容。以下三项检查不需要额外工具：

检查项 操作 预期结果
你的域名/robots.txt 浏览器直接打开 返回内容，且 Sitemap: 指向真实域名
你的域名/sitemap.xml 浏览器直接打开 每一条链接均为线上域名
页面规范地址 打开任一文章，查看页面源代码，检索 canonical 与 og:url 均指向线上域名

三项中任意一项不符合预期，后续优化都不会生效，因为爬虫无法定位到正确的页面。

四、配置修正：url 与 root

4.1 错误表现

打开 sitemap.xml，所有条目均指向本地地址：

4.2 成因

url 与 root 定义在 _config.yml 中，是站点的根地址配置。Hexo 不保存绝对路径，所有绝对地址均在生成阶段由这两项拼接得到，包括 sitemap、canonical、og:url、RSS 以及文章永久链接。

本地调试时将 url 设为 http://localhost:4000，若该配置随产物一同部署，上述所有地址都会指向本地主机。

4.3 连锁影响：canonical 与 og:url

爬虫在页面 <head> 中读取到的规范地址为：

canonical 用于声明页面的规范地址。该值指向 localhost 时，爬虫会判定 localhost 上的页面为正本，线上页面仅为其副本。结果是页面虽被抓取，但规范地址不可访问，因而不会出现在检索结果中。

同理，og:url 错误会导致内容分享至社交平台时，链接指向本地地址。

4.4 正确配置

说明：

  • url 填写线上实际访问地址，结尾不带斜杠；
  • root 在部署于根路径时为 /；
  • permalink 建议使用 abbrlink，避免中文标题出现在 URL 中。中文会被编码为 %E4%B8%AD%E6%96%87 形式，既影响可读性，也可能在分享过程中被截断。

修改后必须重新生成站点，原因见第九节。

五、robots.txt 配置

5.1 现象

访问 你的域名/robots.txt 返回 404。

5.2 成因

GitHub Pages 仅使用仓库中的构建产物。本地新增文件而未执行部署时，线上不存在该文件。

  • Disallow 仅用于屏蔽静态资源目录，不应使用 Disallow: /，该写法会禁止全站抓取；
  • Sitemap: 后的域名必须与线上域名一致，地址错误时爬虫会抓取到无效页面，影响比不配置更差。

七、站长平台验证

7.1 配置位置

在 _config.butterfly.yml 中填写各平台提供的验证码，由主题生成对应的 <meta> 标签：

7.2 验证方式的选择

用户名.github.io 属于二级域名，其 CNAME 记录由 GitHub 管理，因此无法使用 CNAME 文件验证方式。应改用 HTML 元标签验证，或在支持该方式的平台使用 XML 文件验证。

八、验证失败的常见原因：CDN 缓存

现象：验证码核对无误，站长平台仍提示「验证密钥错误」。

原因：GitHub Pages 前置了 CDN，缓存时间为 max-age=600，即 10 分钟。源站更新后，爬虫在缓存有效期内仍会读取旧页面，而旧页面中不含验证标签。

处理步骤：

  1. 使用无痕窗口访问线上页面，查看页面源代码，确认 <meta name="...verification"...> 是否已存在；
  2. 确认存在后等待约 10 分钟，重新执行验证；
  3. 或改用 XML 文件验证，该方式不依赖页面缓存。

由此可得一条通用结论：部署完成不等于线上生效，中间存在缓存延迟。

九、本地与线上不一致：服务的热加载规则

9.1 现象

修改配置后本地预览正常，线上无变化；或页面内容已更新，但配套脚本未更新。

9.2 成因

hexo server 在启动时将配置文件与主题目录读取至内存，运行期间修改这些文件不会被重新加载。

9.3 处理规则

修改内容 本地预览 是否需要重启 hexo server
source/ 下的文章与页面 刷新即可生效 否
_config.yml、_config.butterfly.yml 不生效 是
themes/ 下的模板与样式 不生效 是

十、操作流程与校验清单

10.1 完整流程

hexo clean 用于删除 public/ 与 db.json，避免上一次构建的产物（含旧域名链接）被一并部署。

10.2 部署前校验清单

校验项 校验方式 通过标准
public/sitemap.xml 直接打开 全部为线上地址
public/robots.txt 直接打开 含正确的 Sitemap: 地址
页面规范地址 打开任一文章 HTML，检索 canonical 指向线上地址
站长验证标签 打开 public/index.html，检索 verification 存在对应 <meta>

10.3 部署后校验清单

校验项 校验方式 通过标准
域名/robots.txt 浏览器访问 返回内容而非 404
域名/sitemap.xml 浏览器访问 全部为线上地址
站长平台 提交 sitemap 平台接受并开始抓取

十一、补充说明：github.io 的收录局限

用户名.github.io 属于二级域名，且不在国内备案。百度等中文搜索引擎对此类站点的抓取与收录量明显低于自有域名。

该问题无法通过配置调整解决。若站点主要面向中文搜索引擎，需要绑定自有域名并完成备案。

十二、小结

  1. 站点的绝对地址由 _config.yml 中的 url 与 root 决定，配置错误会使 sitemap、canonical、og:url 同时失准；
  2. 本地新增的文件必须部署后才会出现在线上；
  3. GitHub Pages 的前置 CDN 存在约 10 分钟的缓存延迟；
  4. hexo server 对配置与主题文件不做热加载，修改后需要重启。

以上四项均非技术难题，而是排查时容易忽略的检查点。
